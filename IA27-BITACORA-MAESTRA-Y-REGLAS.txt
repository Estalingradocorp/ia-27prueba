################################################################################
# PARTE 3 — EL MÉTODO "MARCADOR + INTERCEPCIÓN"
################################################################################

Este es el patrón central del proyecto. Todo lo nuevo que se agregue al agente
debe seguirlo.

Principio: un modelo de 7B NO es agentic de forma nativa. No lo fuerces con
prompts lógicos: dale un PROTOCOLO MECÁNICO que el host ejecute y verifique.

1) El modelo emite un MARCADOR al inicio de su mensaje:
       [[NET]] consulta            → buscar en internet
       [[READ]] ruta               → leer archivo o listar carpeta
       [[CMD]] comando             → ejecutar PowerShell
       [[WRITE]] ruta :: cuerpo    → crear/reemplazar archivo
       [[WRITE]] ruta :: cuerpo [[END]]   (el [[END]] es OBLIGATORIO)
       [[DONE]]                    → fin de tarea (modo harness)
2) El sistema NO confía: lo detecta, lo valida, lo ejecuta bajo permisos.
3) El resultado real se inyecta como mensaje [SISTEMA · ...].
4) Se re-pregunta al modelo con ese resultado (AskContinueAsync).
5) Se detectan MENTIRAS: afirmaciones sin marcador → se descartan y se reintenta.

Variantes del método que resultaron protecciones efectivas:
   - Intercepción de negativas      → si dice "no puedo navegar", se busca igual.
   - Detección de alucinación       → si dice "he creado el archivo" sin [[WRITE]],
                                      es mentira: se descarta y se fuerza reintento.
   - Marcador malformado           → [[WRITE]] sin [[END]] NO escribe nada.
   - BUFFER ANTI-FUGAS             → la cola del stream se retiene desde el
                                      último '[' para que ningún marcador, ni
                                      siquiera un fragmento, llegue a la pantalla.

# PARTE 4 — HERRAMIENTAS DEL AGENTE
################################################################################

  [[READ]] ruta
      Lee archivo (máx. 4000 caracteres) o lista carpeta (máx. 150 entradas).
      Libre dentro del área de trabajo; FUERA de ella pide permiso (s/n).

  [[CMD]] comando
      Ejecuta PowerShell con -NoProfile -NonInteractive, cwd = carpeta actual,
      timeout 30 s, salida truncada a 2000 caracteres.
      SIEMPRE pide confirmación (s/n). Nunca autorización automática de sesión.
      Patrones destructivos → advertencia ROJA extra:
        Remove-Item -Recurse -Force, rm -rf, del /s, rd /s, format, diskpart,
        bcdedit, shutdown, restart-computer, stop-computer, reg delete,
        takeown, icacls /reset, clear-disk, initialize-disk,
        set-executionpolicy unrestricted

  [[WRITE]] ruta :: contenido [[END]]
      Crea o reemplaza archivo (UTF-8 sin BOM). Crea carpetas faltantes.
      SIEMPRE pide confirmación con VISTA PREVIA del contenido.
      Idempotencia: misma ruta + mismo turno → se bloquea el duplicado.

  [[NET]] consulta
      Busca en DuckDuckGo HTML y, si falla, en Wikipedia (es).
      Autorización por sesión (NetAutoAllowed) o pregunta individual.

Límites: 5 herramientas encadenadas por turno · 2 rondas de [[NET]] ·
2 reintentos anti-alucinación.

  *** NO PROBAR LAS HERRAMIENTAS ESCRIBIENDO EN LA RAÍZ. *** La raíz de

################################################################################
# PARTE 5 — MODO HARNESS (bucle agéntico autónomo)
################################################################################

Comando: /harness <objetivo>   (alias: /agente)

El agente trabaja solo por pasos:
  1. Plan numerado (solo al inicio o si cambia).
  2. UNA herramienta por paso.
  3. Verifica el resultado real recibido del sistema antes del siguiente paso.
  4. Termina solo con [[DONE]] + resumen.

Salvaguardas: límite de 15 pasos (HarnessMaxSteps) · marcadores malformados no
ejecutan nada · permisos s/n intactos · Ctrl+C aborta en cualquier momento.

# PARTE 9 — PROBLEMAS CONOCIDOS DE LLAMA.CPP (no regresar)
################################################################################

1) --cache-type-k/v q4_0 CORROMPE tokens en algunos GGUF.
   Síntoma: "Hola!ola!", "P P P P", mezcla de tokens ("AtPI", "PPIA").
   SOLUCIÓN: f16/f16 (ya es el valor por defecto en AppConfig).

2) Forzar --chat-template chatml. El template Jinja embebido en algunos GGUF

3) El streaming debe imprimirse token a token. Esperar la respuesta completa

4) Detector de degeneración: si la cola repite un carácter dominante
   ("P P P P", "777777") se trunca y se reintenta con parámetros distintos.

5) Modelos de 7B: no son "agentic" nativos. Hay que forzar el protocolo con
   marcadores + interceptación, no confiar en que vayan a "obedecer" las
   instrucciones del system prompt.

6) Warning de metadatos del .gguf (aparente en cada arranque, INOCUO):
       control-looking token: 128247 '</s>' was not control-type;
       this is probably a bug in the model. its type will be overridden
   Es un problema del .gguf (el token </s> está declarado con el tipo
   equivocado), no del código ni del runtime: el modelo carga y responde bien
   después. No tocar nada por esto. Se anota porque hace ruido.

# PARTE 10 — ANTI-ALUCINACIÓN (todas las trampas instaladas)
################################################################################

El 7B miente de dos formas distintas. Ambas están frenadas:

A) AFIRMA QUE HIZO UNA ACCIÓN SIN HACERLA
   - WriteClaimPattern / CmdClaimPattern detectan "he creado el archivo",
     "archivo creado en", "ejecuté el comando", "quedó guardado"...
   - Si en ese turno no se ejecutó esa herramienta → se descarta la respuesta
     falsa, se imprime [INTERCEPCIÓN] y se le ordena reemitir con marcador.
   - Máximo 2 reintentos; luego se lo dice al usuario (claro).

B) USA RUTAS INVENTADAS
   - BuildEnvironmentInfo inyecta en el system prompt las rutas REALES: usuario
     de Windows, carpeta de trabajo, Documentos, Escritorio, Descargas, fecha.
   - PlaceholderPathPattern bloquea cualquier ruta con "TuNombreDeUsuario",
     "Usuario", "%USERNAME%", "YourName" → no ejecuta nada y se le devuelven
     las rutas reales para reemisión.
   - Alias "documentos / escritorio / desktop / descargas / downloads" se
     resuelven a las carpetas reales del sistema.
   - lastToolPath: la sesión recuerda la última ruta usada, para que
     "en esa carpeta" o "con el título mejoras" se resuelvan solos.

C) MARCADOR MALFORMADO
   - [[WRITE]] sin [[END]] → no se escribe nada → reintento forzado.
   - El cierre [[END]] también evita que el texto de la respuesta del modelo
     ("¿Necesitas algo más?") termine DENTRO del archivo escrito.

# PARTE 19 — LOS HUÉRFANOS: POR QUÉ EL MODELO "NO CARGABA" (corregido)
################################################################################

SÍNTOMA REAL OCURRIDO el 2026-09-27 ~02:58: el portable quedó 10 minutos en
"Cargando el modelo; la primera carga puede tardar..." sin llegar a responder.
La PARTE 8 lo atribuía a "procesos huérfanos de sesiones anteriores" como si
fuera un phenomenon externo. NO LO ERA. Era un bug propio, y por eso volvía.

QUÉ PASÓ REALMENTE
  Había 4 procesos llama-server vivos, con 6,9 a 7,8 GB de RAM cada uno:
      PID   2528   7.665 MB
      PID   3780     757 MB
      PID  11104   1.629 MB
      PID  11948       4 MB
  Total ~13,9 GB sobre 15,9 GB → quedaban 1,6 GB libres. El portable.exe del
  usuario YA HABÍA MUERTO (no había ningún proceso portable vivo): su ventana
  era teatro. Y los 3 servidores grandes competían por 8 núcleos lógicos, por
  eso la carga no avanzaba en vez de fallar rápido.

  O sea: no era que el modelo no cargara. Era que la máquina se había quedado
  sin RAM, y encima el proceso que gospodaba todo eso ya no existía.

POR QUÉ SE PRODUCÍA (esta es la parte importante)
  El código SÍ mataba al hijo: LlamaServerSession.DisposeAsync hace
  process.Kill(entireProcessTree: true), y el catch de StartAsync lo invoca.
  El problema es que eso solo corre si el proceso DESENROLLA el await using.
  Si portable.exe muere de golpe — cerrás la ventana con la X, o lo mata el
  OOM por falta de RAM, o lo mata un taskkill — .NET no ejecuta ningún finally
  y el llama-server queda huérfano con el modelo cargado en memoria.
  O sea: huérfano por muerte abrupta, no por error de lógica. Por eso el
  "Get-Process llama-server | Stop-Process" de la PARTE 8 lo aliviaba pero
  no lo prevenía: era limpiar a mano lo que el código debía hacer solo.

  Además, FindFreePort elige un puerto libre, así que dos sesiones NO chocan
  entre sí: conviven tranquilas mientras cada una se come 7 GB.

LA CORRECCIÓN (tres cosas, todas en el código)
  1) Job Object de Windows — ChildProcessJob.cs (archivo nuevo).
     Se crea un job con JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE y se mete
     llama-server adentro (AssignProcessToJobObject) justo después de
     process.Start(). El kernel mata al hijo SIEMPRE que muera el padre, sin
     importar cómo muera. Si el Assign falla (proceso ya dentro de un job que
     no admite anidamiento), cae a un handler AppDomain.ProcessExit que lo
     mata a mano.
     TRAMPA al implementarlo: el handle del job NO se puede cerrar antes de
     terminar la sesión, porque al cerrarlo el job mata a los procesos que
     contiene. Va guardado como campo en la sesión y se libera en
     DisposeAsync, después de matar al hijo.
     P/Invoke usado: CreateJobObject, SetInformationJobObject (JobObjectExtended
     LimitInformation = 9), AssignProcessToJobObject, CloseHandle. Las structs
     JOBOBJECT_BASIC_LIMIT_INFORMATION / IO_COUNTERS / EXTENDED van marshaleadas
     a mano, así que el layout importa: en x64 BasicLimitInformation ocupa 64
     bytes. Si SetInformationJobObject devuelve false, se cierra el handle y la
     sesión sigue igual por el camino del ProcessExit.

  2) Mutex de instancia única (TerminalApplication).
     Un Mutex llamado "IA27Terminal.portable.model" en los comandos que SÍ
     cargan el modelo: preguntar/run/ask, agent/agente/chat, serve/servidor,
     doctor y la sesión interactiva. Si ya hay otra, el segundo se rechaza
     con exit code 2 y un mensaje que dice cuántos llama-server hay vivos y
     cuántos MB están usando, más el comando de limpieza.
     Los comandos que NO cargan modelo (listar, info, config, help, version,
     descargar) NO toman el mutex: se pueden usar con una sesión abierta.
     OJO, ya me pasó: si envolvés el switch entero en el guard, terminás
     bloqueando listar/config y el usuario los necesita para diagnosticar
     justo cuando hay algo colgado. Por eso el guard recibe un bool.

  3) --log-disable eliminado (LlamaServerSession).
     Este flag apagaba el log de llama-server, y por eso TODOS los archivos en
     logs\ pesaban 0 bytes. Sin log no hay diagnóstico: hubo que adivinar el
     problema mirando la lista de procesos. Ahora los logs se llenan (una
     sesión normal: ~2 KB, 6 líneas de arranque; hay una de 7,5 KB con las
     métricas de la P12).
     OJO: el flag servía para que la salida de llama-server no se mezclara con
     la consola. El log va a un archivo aparte (logWriter), no a la consola, así
     que se puede quitar sin ensuciar la pantalla.

PRUEBA DEL FIX (no aceptar "compiló" como evidencia)
  Prueba del huérfano, la importante:
      1) lanzar `preguntar "hola" --max-tokens 16` en segundo plano
      2) esperar 25 s → verificar que hay 1 llama-server con ~7,8 GB
      3) Stop-Process -Force sobre portable.exe (equivale a cerrar con la X)
      4) RESULTADO: no queda ningún llama-server. El Job Object lo mató.
      Con el código anterior ese mismo paso dejaba un huérfano de 7,8 GB.
  Prueba del mutex:
      sesión A con preguntar viva → segundo preguntar se rechaza (exit 2),
      mientras listar y config show funcionan con exit 0.

  Tiempos medidos con el fix: carga 53,2 s y 58,5 s en dos corridas limpias.
  Coincide con los ~60 s que la PARTE 8 ya anotaba.

HALLAZGO NUEVO QUE EL LOG REVELÓ AL QUITAR --log-disable
  Al volver a escribir el log apareció de inmediato un aviso de llama-server:
      CORS is set to allow all origins ('*') and no API key is set
      this can be a security risk (cross-origin attacks)
  Ver PARTE 20. Sigue sin resolverse.

  Esto es un buen ejemplo de por qué el log servía: el aviso estaba ahí desde
  el primer arranque, invisible solo por el flag.

TRAMPA DE ENTREGAS: LA v0.1 NO TIENE ESTE FIX
  Todo esto está en el publish actual y en la v0.2 congelada. La v0.1 es una

# PARTE 20 — CORS Y API KEY DEL LLAMA-SERVER (decisión abierta, sin tomar)
################################################################################

HALLAZGO
  Cada arranque de llama-server escribe este aviso en el log:
      CORS is set to allow all origins ('*') and no API key is set
      this can be a security risk (cross-origin attacks)
      more info: https://github.com/ggml-org/llama.cpp/pull/25655

POR QUÉ NO ES ACABADO
  El servidor ya se levanta con --host 127.0.0.1, así que NO es alcanzable
  desde la red. Pero con CORS en comodín y sin API key, cualquier página web
  abierta en el navegador puede pegarle a http://127.0.0.1:<puerto> y leer la
  respuesta del modelo. El puerto es aleatorio (FindFreePort), lo que baja la
  probabilidad pero no la anula: una página podría barrer puertos.
  O sea: la amenaza es local, desde el navegador, no desde la red.

ESTADO: NO RESUELTO. No se cambió nada de esto al aplicar el fix de la P19.

OPCIONES (cuando se decida)
  a) Levantar llama-server con un --api-key aleatorio por sesión y mandarlo en
     la cabecera de cada request. Es lo que recomienda el aviso upstream.
  b) Restringir el CORS en vez de dejarlo en '*'.
  c) Dejarlo como está, aceptando el riesgo local, y que quede escrito que se
     aceptó a sabiendas.

  Mientras no se elija una, esto es una decisión pendiente, no un descuido.
